# Repo File Structure & Naming Cleanup (Pass 2)

## Context

Pass 1 of repo cleanup (commit `46eeb1bc`) gitignored large binary assets and removed unused junk files. This pass focuses on the project's file/folder structure and naming, to make the repo read more like a conventional codebase, while respecting the engine's real constraints:

- The compiled `Data/Scripts.rxdata` (what `Game.ini`'s `Scripts=` setting actually points at, and what mkxp-z's closed-source runtime loads) contains a single tiny stub script. That stub's source is generated by our own tracked `scripts_combine.rb` and, when decompiled, does nothing but `load_scripts_from_folder("Data/Scripts")` — recursively eval-ing every `.rb` file under that path alphanumerically, depth-first. Critically, **that path is a plain string embedded in our tracked tooling, not something baked into the mkxp-z binary** — confirmed by decompiling the stub and successfully round-tripping a modified copy through the same decompress → edit → recompress → `Marshal.dump` pipeline `scripts_combine.rb` uses. This means the human-authored `Data/Scripts/` folder can be relocated to anywhere on disk, independent of where the *compiled* `Scripts.rxdata` cache lives (which stays at `Data/Scripts.rxdata`, matching `Game.ini`).
- Top-level asset folders expected by the runtime/RPG Maker XP conventions (`Audio/`, `Graphics/`, `Fonts/`, `Plugins/`, `Data/`) remain effectively fixed — we have no way to verify or override what the closed-source runtime expects there.
- `PBS/*.txt` and `Text_english_core/*.txt` filenames are read by our own Ruby compiler code (`Data/Scripts/021_Compiler/`), not the runtime directly, so they *can* be renamed as long as the corresponding code is updated in lockstep.

Given the mixed risk profile, this cleanup is split into four independently testable phases, executed in order, each verified in `Game.exe` before moving to the next.

## Goals

- Improve clarity of the project's file/folder structure and naming so it better resembles a conventional codebase.
- Separate human-authored source code from generated/compiled binary data, which today are nested together under `Data/` (itself almost entirely gitignored, generated content).
- Do this without changing any runtime-visible behavior (load order, data compiled, UI text, save compatibility).
- Keep each change small enough to verify manually (no automated test suite exists — see `CLAUDE.md` verification guidance).

## Non-goals

- Renaming individual `.rb` script files within the scripts folder (hundreds of files, already reasonably descriptive — out of scope for this pass, could be a future pass if desired).
- Any change to the `NNN_` numeric-prefix load-order mechanism itself (explicit manifest/require system was considered and explicitly rejected as higher-risk than warranted).
- Touching top-level engine-owned asset folders (`Audio/`, `Graphics/`, `Fonts/`, `Plugins/`) or root engine binaries (`Game.exe`, DLLs, `Game.ini`, `Game.rxproj`).

## Phase 1 — Root directory cleanup

**Change:** Create a new `Tools/` folder at repo root. Move into it, as a unit (they reference each other by sibling-relative paths):

- `animmaker.exe`, `animmaker.txt`
- `extendtext.exe`, `extendtext.txt`
- `knownpoint.bmp`, `selpoint.bmp`
- `townmapgen.html`
- `scripts_extract.rb`, `scripts_combine.rb`
- `Essentials Engine wiki.url`

Confirmed via grep across `Data/Scripts/` that none of these filenames are referenced anywhere in the Ruby scripts. `Game.exe`, its DLLs, `Game.ini`, `Game.rxproj`, `mkxp.json`, and `soundfont.sf2` (referenced by relative path inside `mkxp.json`) stay exactly where they are — moving them has no naming-clarity benefit and only adds risk.

**Risk:** Very low. Nothing in the compiled or scripted game logic depends on these paths.

**Verification:**
1. Launch `Game.exe`, confirm normal boot to title screen with no missing-file errors, confirm `soundfont.sf2`-backed MIDI BGM still plays if applicable.
2. From the new `Tools/` folder, launch `animmaker.exe` and `extendtext.exe` directly and confirm they still function (they depend on sibling files `knownpoint.bmp`/`selpoint.bmp` via relative path).
3. `git status` review before commit to confirm only the intended moves are staged.

## Phase 2 — Relocate `Data/Scripts/` to a top-level `Scripts/` folder

**Change:** Move the human-authored scripts folder out from under `Data/` (which is otherwise ~100% generated, gitignored binary content) to a new top-level `Scripts/` folder, a sibling of `Data/`, `Audio/`, `Graphics/`, etc. The compiled `Data/Scripts.rxdata` cache is unaffected and stays exactly where it is — `Game.ini`'s `Scripts=Data\Scripts.rxdata` setting does not change.

Steps:
1. `git mv Data/Scripts Scripts`.
2. Update the two default path parameters in `scripts_extract.rb` and `scripts_combine.rb` (`path = "Data/Scripts"` → `path = "Scripts"`) — these control both directions of the extract/combine round-trip.
3. Regenerate the embedded loader stub in `scripts_combine.rb`: decompile the `txt` blob in `createLoaderScripts`, change its `load_scripts_from_folder("Data/Scripts")` call to `load_scripts_from_folder("Scripts")`, recompress, and replace the blob. (Mechanism already validated — see Context.)
4. Update the one other reference: `Dir.all("Data/Scripts")` in `001_Technical/003_Intl_Messages.rb` (used by the in-game translation-text gatherer) → `Dir.all("Scripts")`.
5. Update `.gitignore`: remove the `!Data/Scripts/` carve-out from the `Data/*` ignore block (no longer needed — `Scripts/` is tracked directly as its own top-level folder, outside the `Data/*` ignore rule entirely).
6. Update `README.md` and `CLAUDE.md` path references (`Data/Scripts/` → `Scripts/`).
7. Regenerate `Data/Scripts.rxdata` by running the updated `scripts_combine.rb` (requires local Ruby, per README) so the compiled cache matches the new stub and new folder location.

**Risk:** Moderate — this is the one change in the whole cleanup that touches a compiled/binary artifact (`Data/Scripts.rxdata`) rather than pure text/folder renames. The recompile step is mechanical and was validated end-to-end in isolation (decompress → edit → recompress → `Marshal.dump` → `Marshal.load` → re-inflate, byte-identical result), but it must still be exercised for real via `Game.exe` before trusting it.

**Verification:**
1. Regenerate `Data/Scripts.rxdata` via `scripts_combine.rb` and confirm it runs without error.
2. Launch `Game.exe` and confirm normal boot to title screen — this is the critical test, since a broken loader stub means the game fails to boot at all.
3. Exercise a broad slice of functionality (overworld movement, opening the menu, a wild battle, saving/loading) to confirm scripts loaded correctly from the new location.
4. Force a full recompile (Ctrl+boot) to confirm PBS compilation (unrelated to this change, but a good general-health check) still works.
5. Trigger the translation-text gatherer (if accessible without a full translation workflow) or otherwise confirm `003_Intl_Messages.rb`'s updated path doesn't error.
6. If anything fails to boot, this phase's commit should be reverted rather than debugged live — re-attempt after diagnosing offline, since a broken script loader blocks all further testing.

## Phase 4 — PBS / `Text_english_core` filename review

**Change:** Candidates to evaluate and rename, each requiring a matching code change:

- `PBS/pokemon.txt`, `pokemon_forms.txt`, `pokemon_metrics.txt` — rename to align with the `Species`/`SpeciesMetrics` `GameData` class names (exact new names TBD at implementation time, e.g. `species.txt` family). Requires updating the `PBS_BASE_FILENAME` constant in `Scripts/010_Data/002_PBS data/008_Species.rb` (and `010_SpeciesMetrics.rb`), since `021_Compiler/001_Compiler.rb#get_all_pbs_files_to_compile` matches sibling files by that constant's prefix.
- `PBS/cup_*_pkmn*.txt` — reconcile the `pkmn` abbreviation with the spelled-out `pokemon` used elsewhere in PBS filenames.
- `PBS/Shadow Pokémon backup/` — rename to an ASCII-safe `PBS/shadow_pokemon_backup/`. Confirmed via grep that no script reads this folder (it's inert archival data), so this is a pure filesystem rename.
- `Text_english_core/*.txt` (SCREAMING_SNAKE_CASE) vs. `PBS/*.txt` (lower_snake_case) — investigate how `Text_english_core` basenames are resolved (likely also centralized, similar to `PBS_BASE_FILENAME`) before committing to specific renames; document the finding and either reconcile casing or record why it's intentionally different.

Exact final naming choices for the `pokemon.txt` family and `cup_*_pkmn*` files will be confirmed with the user at implementation time before renaming, since these are subjective/taste calls, not mechanical cleanups.

**Risk:** Highest of the four phases — requires coordinated renames of both a data file and the code that names it, and any mismatch silently breaks data compilation for that category.

**Verification, per file/family renamed:**
1. Full recompile (Ctrl+boot or F9 → "Fully compile all data") and confirm the affected data compiles without error.
2. Open the relevant F9 debug data editor for that category and confirm it loads and saves correctly.
3. For `Text_english_core` files specifically, confirm in-game text (names, descriptions, dex entries as applicable) still renders correctly.
4. Commit each renamed family separately.

## Rollout

Four commits minimum (one per phase), each preceded by the verification steps above. If a phase's verification fails, fix or revert that phase's commit before starting the next phase — phases are not parallelized specifically so a regression stays isolated to a small, known diff. Phase 2 (the `Scripts/` relocation) is the load-bearing one: everything in Phase 3 operates on its result, so Phase 2 must be fully verified — including a real `Game.exe` boot — before Phase 3 begins.
